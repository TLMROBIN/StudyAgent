# 学生会话连续性、图片与 M9 体验核查

日期：2026-11-05。范围：只读代码核查、远端运行状态、现有定向测试、构造 Prompt 验证；本轮未修改产品代码或部署。已通过反馈 #164 定位学生，并只读核查对应作文会话 #14109；未进行 M9 真机复现或学生端视觉验收。

## 总体判断

应把“回到原会话”“模型保留原题”“图片持久化恢复”“拍摄完整性”“系统栏适配”和“新手路径”分别验收。后台继续生成已经存在，但并不等于学生下次进入时自动回到原题；聊天记录持久化也不等于完整记录都送进模型。

## 已证实的代码行为

### 1. 已完成回复后的会话没有通用自动恢复入口（高优先级）

- `frontend/src/views/StudentChat.vue:122,134`：消息和当前会话 ID 都是组件内状态。
- `frontend/src/App.vue:227`：RouterView 未缓存聊天组件；切换路由会卸载。
- `StudentChat.vue:1826`：进入页面只尝试恢复 pending 请求和最近的非空草稿。`restoreLatestDraftContext()` 在没有草稿时直接退出；`done` 会清除 pending 和已发送草稿。
- 因此，回复完成、输入框为空、切到成长/反馈再返回时，没有自动恢复此前会话的机制。这支持“回来像换了一题”的反馈，但不能据此断言特定作文记录已丢失。

建议：按用户保存上次有效会话指针，与 pending 请求和草稿分开管理；恢复优先级为生成请求、明确选择的会话、上次有效会话。主动新建、删除、归档和账号切换必须具有明确语义；不得随意选中其他历史记录充当恢复。恢复时显示实际会话标题及“继续上次问题”。

### 2. 模型历史固定截到六条消息（高优先级）

- `backend/services/socratic_service.py:256` 使用 `history[-6:]`。
- 构造四轮对话，首条含作文原题：输入历史八条，模型收到历史六条，原题锚点不在 Prompt 中。这个问题不依赖退出页面，也可能在持续对话中出现。
- `backend/routers/chat.py:138` 的短追问主题取最后一条用户消息，未必是原题；短回答补充机制不能替代原题持久上下文。
- 后续纯文字轮次的 history 只取 role/content；图片理解摘要传入使用本轮 `image_understanding`。未看到在此路径按历史附件恢复原图摘要的逻辑，因此图片题追问也需要纳入连续性修复范围。

建议：保留原题/材料、当前子问题、学生已经确认的步骤、导师最后一个问题及必要图片摘要，配合最近对话和长度预算。学生陈述、模型推测、已确认事实应区分；不能把摘要推测写成学生事实。继续遵守苏格拉底引导与不直接给最终答案约束。不要简单无限增加历史长度。

### 3. 图片切换后的恢复存在两条不同路径（高优先级）

- 新发送消息先使用本地 blob URL；离开页面时 `clearLocalAttachmentUrls()` 释放它。
- `openConversation()` 从服务器读取附件元数据并执行 `preloadMessageAttachments()`，表明历史附件重载路径存在，不能直接认定文件未保存。
- `useAuthorizedAssets.ts` 通过鉴权请求拉取图片，预加载使用 `Promise.allSettled`；失败后气泡可一直显示“图片加载中”，缺少就地失败及重试状态。
- `done` 分支更新助手回复及知识库 assets，未见把本轮用户附件从临时 URL 替换成服务器附件元数据的步骤。

建议：恢复会话后使用持久附件 ID/URL 重新鉴权加载；本轮发送完成后用服务器附件元数据替代临时地址；气泡提供加载、失败、重试状态。不要通过取消附件鉴权解决显示问题。

## 尚不能定因的问题

### 4. 拍摄图片拉伸、裁切（高优先级，待真机复现）

- Android 两个壳均走 TakePicture 输出 URI，当前所查回调未见位图拉伸操作。
- `chatImageUpload.ts` 按统一比例缩至长边 2000，再以 JPEG 0.85 重编码；没有自动裁切。压缩可能降低整页小字清晰度，但不足以证明“几乎完全丢失”的原因。
- 手动裁剪存在独立操作；聊天缩略图 CSS 为 `object-fit: contain`，预览为自动高度。
- `chat_attachment_service.py` 校验后直接写入上传字节，当前保存路径没有再裁切。

下一步必须比较同次拍摄的相机原文件、前端处理后的上传文件、服务器附件，以及气泡/放大预览的宽高比、边缘内容和方向。覆盖横竖拍、旋转 EXIF、长题、整页文字和 M9 专有来源。区分原图完整但预览异常、预处理损坏、相机输出异常，避免错误修复环节。

### 5. M9 系统栏遮挡（高优先级，待确认 APK 与 WebView）

- 两个壳均设置 `setDecorFitsSystemWindows(false)`，然后对 WebView 设置 systemBars padding；工具箱还处理 IME 底边。
- 这说明已有适配意图，但 WebView 本体 padding 不等于已在 M9 验证所有 fixed/弹窗视口。不能宣称“完全没有适配”，也不能因有 Insets 代码便宣称已修好。
- 查看题图弹窗依赖顶部默认关闭按钮，正文内没有独立关闭入口，受系统栏遮挡时恢复路径不足。

建议：优先确保原生内容容器实际位于可用区域，协调系统栏、刘海、键盘 Insets；Web 弹窗再做可视区限高与内部滚动，并提供正文/底部大触控关闭按钮。记录学生实际 APK 版本、Android/WebView 版本；同时覆盖工具箱和独立壳、横竖屏、三键导航、键盘展开、图片放大及返回键。

## 新手路径建议（基于代码结构，非实际视觉评分）

现有页面已经有“更多”和隐藏引导设置，不能简单把反馈解释成“把所有设置都收起来”或只改配色。主要问题是任务连续性、入口语义和失败恢复不明确。

- 首屏明确主动作：输入问题/添加题图 → 检查完整图片 → 发送。
- 图片来源入口保留适合 M9 的拍摄、照片、文件能力，以“添加题图”统一组织，并解释适用场景。
- 回到答疑时明确“继续上次问题：实际标题”，同时保留清楚的新问题入口。
- 通用引导标题不能替代当前题目的识别；生成中、已保存、恢复失败分别给出下一步。
- 暂不做全站视觉重构，先修复上述可靠性与可达性，再用新生首次使用任务评估是否能独立完成首问及继续追问。
